# 活动封面图片压缩说明

初始记录日期：2026-09-09；清理更新：2026-10-10。当前选定方案为 JPEG Q88。下文部署和验收数据是历史记录，不代表本轮重新核验了生产状态。


## 新增素材压缩规则（2026-09-21）

- 图片或 GIF 的原始文件大小**不超过 500 KB（含 500 KB）**时，默认不尝试压缩，保留原文件。
- 图片或 GIF 的原始文件大小**大于 500 KB**时，才进入压缩评估流程；压缩后必须同时检查文件体积、分辨率、画质和GIF 的帧数、动画是否正常。
- 压缩结果如果没有变小、画质不合格或 GIF 动画被破坏，则保留原文件，并记录未采用压缩结果的原因。
- 这里的 500 KB 按 `500 × 1024 = 512,000` 字节计算；判断依据是原始文件大小，不是缩略图、毛玻璃图或压缩候选文件大小。
- 自 2026-09-22 起，所有新增封面（静态图片和 GIF）均不再生成毛玻璃衍生图，新增 `catalog.json` 条目也不再写入 `glass_path`。
- 旧资源已经存在的毛玻璃文件继续保留，本规则不触发批量删除；后续如需清理旧资源，应单独评估引用关系。
## 当前方案：JPEG Q88（用户确认）

- 高清原图按 JPEG Q88 编码，保持原始宽高、原有色度采样，优化编码，不裁切、不缩放。
- 原件仍在各画师原目录；交付件存放于 `jpeg-q88-v1/`，映射及校验值记录在 `jpeg-q88-manifest.json`。
- 每张素材比较 Q88 编码、无损 JPEG 系数优化与原件复制的体积，选择最小者，避免压缩后反而变大。实际93张高清封面全部使用Q88；其余194张小素材采用无损优化或原样复制。
- Q88不是“保留88%画质”；本次是有损压缩，不承诺逐像素一致。原件和色彩配置保留。
- 93张高清封面：50,096,189 → 33,002,793字节（50.096 → 33.003 MB），减少34.1%。
- 全部287份素材：54,564,002 → 37,415,846字节（54.564 → 37.416 MB），减少31.4%。
- 构建脚本：`backend/scripts/build_cover_jpeg.py`。依赖 Python、Pillow、jpegtran。再次执行只允许相同输出；检测到发布文件内容不同时拒绝覆盖，必须新建发布版本。
- 本地交付开关：`ACTIVITY_COVER_JPEG_ENABLED=1`；默认关闭。启用后有映射的素材使用 Q88 交付件，URL 带内容哈希；未映射素材继续使用原件，服务端原件解析仍指向原件。
- 验收：287个原件及交付件SHA256、JPEG解码、尺寸和体积核验通过；7项专用测试、323项前端测试通过。微信模拟器287/287下载及getImageInfo解码成功；首页11/11卡片显示成功；重启后15/15首页素材命中持久缓存。公网93条封面记录、287个JPEG链接均验证成功。尚未覆盖本轮iOS/安卓真机验收。
- 当前状态：2026-09-09已部署JPEG Q88。服务器原件与交付件均保留，线上接口已返回带内容版本的Q88目录链接，后端服务active。本次图片URL切换不要求前端重新发版；已有客户端需刷新活动列表获取新地址，旧地址保持有效。100MB持久缓存属于此前本地前端改动，其线上可用性仍取决于对应前端版本是否发布，不能把本次后端切换等同于缓存前端已发布。
- 历史生产部署通过 systemd 独立配置 `30-cover-jpeg-q88.conf` 启用 `ACTIVITY_COVER_JPEG_ENABLED=1`；回滚设为 0 并重启服务，原件地址仍可用。

生成命令（在项目根目录）：

```sh
python3 backend/scripts/build_cover_jpeg.py
python3 -m unittest discover -s backend/tests -p test_cover_jpeg_delivery.py -v
```
