# 图片或名称录入桌游：BGG 候选选择与 OCR 方案

更新：2026-09-13。名称搜索、BGG 候选资料、版本选择和确认录入已在 v3.3 实施，实际接口与数据设计见 [名称录入实现](14-name-intake.md)。本文件继续记录图片识别的后续方案；本轮没有新增图片上传、OCR 服务或模型调用。

## 1. 推荐方案

录入只有一个主向导，两种输入在 BGG 查询前汇合：

1. 用户选择“输入名称”或“上传图片”。名称直接成为搜索词；图片经 OCR/视觉模型提取名称，展示可修改的搜索词。
2. 后端查询 BGG Search，并获取候选的 Thing 详情；界面展示 BGG 真实返回的候选资料。
3. 用户按封面、名称、年份、本体/扩展等信息选择正确条目；同一作品下的语言、出版社或印次差异，继续从该作品的版次列表选择。
4. 确认所选资料后再登记归属、购入日期、状态等实物信息，最后保存。

查找与选择阶段不创建正式作品或实物。识别和本地重复检查不能替用户选定条目；已有本地作品只在候选上提示“已收录”，确认后复用。BGG 无正确结果或不可用时，才提供明确的“未找到，手工录入”后备路径。

图片第一版一次处理一盒，支持相机和相册；多盒照片提示选择主体、裁剪或重拍，整架批量建库以后单独扩展。名称输入不依赖视觉服务或临时图片；视觉服务关闭时名称查询仍可用。

推荐先用百炼 **Qwen3-VL-Flash 非思考模式**做样本验证，一次调用提取可见文字、可能的作品名称、本体/扩展和版本线索。需要验证更复杂封面时用 Qwen3-VL-Plus 对照。具体模型 ID、地域和调用地址由服务端配置，验证通过后固定快照版本；首版不自动连续升级多个模型。

这是依据接口能力和接入复杂度作出的工程选择，尚没有本项目桌游照片上的命中率结果。官方支持图片输入；Qwen3-VL 的非思考模式支持 JSON Object 输出，服务端仍须验证字段和类型，不能把合法 JSON 当成正确识别。[视觉理解](https://help.aliyun.com/zh/model-studio/vision/)、[结构化输出](https://help.aliyun.com/zh/model-studio/qwen-structured-output)

另一条路线是腾讯云 `GeneralAccurateOCR`：能返回文字、坐标及文字识别置信度，适合作为字词识别的对照或后续补充。仅凭 OCR 结果还需要本地别名或作品匹配，才能处理“中文盒名 → BGG 英文条目”；不必在首版同时接两套服务。[腾讯云高精度 OCR](https://cloud.tencent.com/document/product/866/34937)

## 2. 识别和资料查询各自负责什么

| 环节 | 输出与边界 |
| --- | --- |
| 名称输入 / 图片识别 | 名称原词或从图片看见的名称；可能的英文搜索词另标为推测，均用于 BGG 搜索 |
| BGG 查询 | 用搜索词查真实条目，再取 Thing 详情获得封面、人数、时长、版次和完整来源数据 |
| 本地重复检查 | 为 BGG 候选附加已收录状态和本地 game_id，确认后复用；不替代 BGG 候选页 |
| 用户确认 | 选择正确条目和版次，修改中文展示名，再确认这一盒归谁、状态及购入时间等 |
| 保存 | 按现有权限登记作品和实物；识别模型不产生真实 BGG ID，不决定所有权，不直接写库存 |

例如照片只显示“方舟动物园”，模型可能建议搜索 `Ark Nova`。这个英文名称是待核对线索，仍须与查询返回的作品及封面比较；查不到时允许修改搜索词或手工录入。不能把中文名称直接翻译后默认视为 BGG 官方名称。

模型读取到的人数、时长、年份也仅为待核对线索；绑定 BGG 时资料来自真实 Thing 响应。无 BGG 的游戏走手工资料模型，用户明确采用的字段才写入人工覆盖值。识别产生的别名不直接污染全局别名或中文分类映射。

模型返回示意，非真实识别结果：

```json
{
  "subject_count": 1,
  "observed_titles": ["方舟动物园"],
  "observed_publisher": null,
  "game_type_hint": "unknown",
  "edition_hint": null,
  "search_terms": [
    {"text": "方舟动物园", "basis": "visible_text"},
    {"text": "Ark Nova", "basis": "inferred_alias"}
  ],
  "issues": []
}
```

不向用户显示模型自报的“99% 正确率”。候选显示可核对的封面、名称、年份、类型和匹配原因；相近版本标为待确认。

### 候选资料与版次

BGG Search 按名称找条目；Thing 的 `versions=1` 获取条目下的版本信息。因此“搜到哪些游戏/扩展”和“这款游戏的哪一语言或出版版次”分两层处理。[BGG XML API2](https://boardgamegeek.com/wiki/page/BGG_XML_API2)

界面需要接收以下投影，完整 XML/JSON 仍按既定方案保留：

| 层级 | 返回字段 |
| --- | --- |
| 作品候选 | candidate_id、bgg_id、名称与别名、类型、作品年份、封面/缩略图、人数、时长、detail_state、已收录 local_game_id |
| 版次候选 | bgg_version_id、所属 bgg_id、版次名称、版次年份、语言、出版社、该版封面/缩略图；来源未提供的字段为 null 或空集合 |
| 选择状态 | 当前搜索词、候选版本号、选中的 candidate_id 和 bgg_version_id；没有可核对版次时明确选择“版次未确定” |

用户先选作品候选，再在其资料页核对版次。不能把作品年份当作所选版次年份，也不能将未带版本封面的作品图标成该版本实物图；界面标注封面来源。没有正确条目可回去改词，没有精确版次可保留已选作品并手填版次文字。

## 3. 后续 OCR 如何接入已完成的名称流程

当前小程序已有独立 boardgame_entry 向导：名称 → BGG 搜索 → 候选资料 → 选择版次 → 确认录入。BGG Search 分页、私有 Thing 预览、完整来源保存、版本投影、候选所属校验、库存快照及确认幂等均已实现，见 [v3.3 实际契约](14-name-intake.md)。不再新建另一套 BGG 搜索/录入任务表，也不继续使用上一稿的 boardgame-intake-jobs 路由草案。

OCR 后续只补搜索前的图片入口：上传 → 提取名称和搜索线索 → 用户核对或改词 → 进入现有名称搜索。模型不能产生可信 BGG ID、选择版本或写入库存；名称录入在视觉服务关闭时继续工作。

建议新增但尚未实现：

| 接口 | 职责 |
| --- | --- |
| POST /boardgame-recognition-images | 上传一张图片，返回私有 image_id、尺寸和到期时间 |
| POST /boardgame-recognition-jobs | image_id 发起识别，返回 202；UUID 幂等键 |
| GET /boardgame-recognition-jobs/{id} | 私有识别状态、可见文字、推测搜索词及问题 |
| POST /boardgame-recognition-jobs/{id}/retry | 失败重试，校验 revision 和调用次数上限 |

识别结果核对后直接使用 GET /bgg/search，其后的 /boardgame-intake-previews 和 /boardgame-intakes 均复用。图片和识别阶段不创建游戏，不把用户选择过程交给模型。最多3个去重搜索词是后续图片流程的建议；当前名称入口每次搜索用户确认的一个词。

## 4. 图片与识别任务的数据边界

后续建议独立 boardgame_recognition_images 与 boardgame_recognition_jobs，分别保存私有图片信息，以及识别状态/结果、用户、模型/提示词版本、用量、错误、尝试次数和租约。只存视觉环节，不重复存正式 BGG 来源和入库结果；两表当前未迁移、未计入34张领域表。

名称预览现在复用导入任务持久化，尚未设置短期到期清理；不能将识别图片的删除策略套用到已确认的 BGG 来源与幂等记录。库存 bgg_version_snapshot 已通过0015保存用户所选版次，不依赖未来识别任务。

## 5. 建议的图片生命周期

以下是后续设计值，尚未启用：

- 一次一盒，相机或相册输入；多盒需选择主体、裁剪或重拍。后端按解码结果接受 JPEG/PNG/WebP，流式限制8 MiB并限制像素，处理方向并去掉EXIF；模型副本建议长边2048px、4 MiB内。
- 图片存放于公开 MEDIA_ROOT 之外，只有发起账号可用。模型由后端传图，不附带用户账号、活动或对局数据；API Key仅在服务端。
- 图片和副本默认24小时到期，识别结果默认7天。清理需协调有效租约，并与正式游戏封面、已确认版本快照分开。
- 用户、图片哈希、模型和提示词版本共同决定未过期缓存；不跨用户共享私有结果。限制并发、日额度和总重试次数；上游超时可能已经计费，不能承诺只收费一次。
- 图片内文字仅作待提取数据，不执行其中的代码、URL或指令。结果经受限JSON校验后显示给用户，不能自动污染共享别名和分类翻译。

## 6. 小程序接入与实施顺序

1. 名称录入已完成，先保留这一条稳定路径；视觉规范沿用 [小程序UI参照](../../../prototype/design-system/miniprogram-ui-reference.md)。
2. OCR 开发时在搜索页添加“拍照/相册”入口，识别后显示可编辑名称，再调用同一搜索方法；不会再次跳入批量导入页。
3. 识别失败、相册取消、权限拒绝、模糊和多盒图片均保留名称输入与手工后备路径。
4. 使用桌游照片样本对照模型后，再固定模型快照、地域、限额和成本；相机/相册、上传合法域名、图片处理与微信真机另行验收。

## 7. 成本估算

核对日期：2026-09-13。百炼华北 2（北京），单次输入不超过 32K Token，普通实时推理：Qwen3-VL-Flash 输入/输出分别为 **0.15/1.5 元每百万 Token**，Plus 为 **1/10 元每百万 Token**。地域或价格档位不同应重新计价，不依赖免费额度。[官方价格](https://help.aliyun.com/zh/model-studio/model-pricing)

假设每次包含图片在内的输入为 2,000 Token、输出为 500 Token：

| 模型 | 一次模型调用 | 1,000 次模型调用 |
| --- | --- | --- |
| Flash | 0.00105 元 | 1.05 元 |
| Plus | 0.007 元 | 7 元 |

计算式为 `(输入 Token × 输入单价 + 输出 Token × 输出单价) / 1,000,000`。这是假设用量下的模型费用，不是实测单张成本；图片分辨率、提示词、重试与二次调用都会改变用量，另计存储、流量等费用。应按供应商返回的 usage 统计实际成本，BGG 等待时间也单独记录。

## 8. 后续 OCR 验证

准备约50张可核对答案的照片，覆盖中文/英文封面、扩展、相近版本、反光斜拍和未收录游戏。记录看清名称的比例、Top1/Top3候选命中率、本体扩展混淆、耗时和供应商usage；分别比较Flash与Plus，不用宣传数字代替桌游样本结果。

OCR新增回归需覆盖私有图片、跨账号、过期、重复上传、多盒、错误JSON、限额、上游超时及清理租约。名称搜索与确认链路的回归继续复用v3.3测试，尤其是未确认不入库、明确选版、已有作品复用和重试不重复建盒。

本次只完成名称录入代码及相应验证，未调用模型、未测试真实照片、未新增识别API或图片表。以上模型和价格保留此前调研结果，实际开始OCR接入时重新核对供应商状态。
