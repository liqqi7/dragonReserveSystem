## 1. 最想开与多维筛选

取有效 active/frozen 提名，排除已取消、已流局、已删除活动。active 仍须具备成员和创建者/报名者资格；frozen 保留截止时意愿。一个用户同活动同游戏仍只有一票，重复点击不能刷人数。

| 字段/展示 | 公式 |
| --- | --- |
| `nomination_count` 累计提名人次（主指标） | `COUNT(*)`，等于各活动提名人数之和；跨场同人重复计入 |
| `activity_count` 提名活动场数 | `COUNT(DISTINCT activity_id)`；与人次并列显示，不再与人次相加造分数 |
| `my_activity_count` 我的提名次数 | 仅当前用户的有效提名活动数 |

全体按 nomination_count 降序，同值并列；activity_count 降序和 game_id 升序仅稳定显示次序。我的按 my_activity_count 降序，另列累计提名人次。小李在 A/B 两场都提名、小王在 A 提名，合计 **3 人次、2 场**；小李的我的为 2 次，不把他跨场去重成 1 次。A 场取消后只余 B 的 1 人次。

筛选支持活动多选与月份、自然季度、年度、自定义日期的组合：活动列表内是 OR，活动与时间之间是 AND；月份/季度/年度是时间选择的互斥粒度，统一成区间，不要求用户同时填月和季。默认全部已记录，时间预设使用完整自然期间，不以过去 30/90/365 天代替。季度 Q1=1–3 月、Q2=4–6 月、Q3=7–9 月、Q4=10–12 月；参数及非法组合见 03。

提名日期取 activity.start_time 的上海日期，对局日期取 played_on；同一时间筛选可能得到不同提名数和开局数，这是两个事实的日期不同。活动结束后补录的局按实际游玩日期统计，不按录入日期。活动筛选对局用 original_activity_id，活动硬删除后仍可从快照提供历史筛选项；提名本身随删除活动消失。

所有总览、榜单、比较组、趋势、来源钻取共用同一过滤器并回显实际条件。趋势可按 day/month/quarter/year/activity 分组；分组粒度与筛选区间独立。没有所选活动关联的独立局不会误入活动筛选。尚未举行活动的有效提名可进入未来月份或季度，实际完成局不能填未来日期。

一期不另建长期 wish 表，不把 BGG wanting、wishing、wanttoplay 或签到人数自动计作提名；选择多个扩展也不会重复增加主游戏提名人次。

## 2. 实际对局统计的基础集合

全体完成局：`publication_status='published' AND status='completed' AND stats_exclusion!='all'`，含已发布的活动内外记录。我的在此集合增加 `EXISTS(玩家 JOIN people，people.user_id = 当前用户)`；不是按 created_by、报名或打卡筛选。历史导入记录暂为 held，即使已经 completed，也不进入任何公开榜单；不得用 origin 筛选绕过 held。

先在对局层构造唯一 play_id 集合，再分别关联玩家、队伍、扩展聚合。避免一局 4 人 × 2 扩展的联表把一局数成 8 局；跨明细聚合时使用独立子查询/CTE 或 COUNT(DISTINCT play_id)。团队成员的参局次数各 1，但整个俱乐部只增加 1 局。

一期直接从业务表按索引聚合，不维护可手改的 want_count/play_count 或永久排行榜副本。更正事务提交后的下一次查询读最新结果；以后若引入短缓存，须在更正、作废、恢复、合并和提名状态变更时失效相关键，不能让详情已更正而榜单长期残留旧成绩。

| 指标 | 分子 / 分母及范围 |
| --- | --- |
| 完成开局数 | 基础集合中对局 ID 数，每局只计一次；无成绩仍计 |
| 游戏款数 | 主游戏 game_id 去重，扩展作为附属使用不增加款数 |
| 开的最多 | 按主游戏分组的完成开局数；同款当天多局逐局计 |
| 玩家参局数 | 基础集合中该 person_id 实际出现的不同 play_id 数 |
| 参局人次 | 每局实际玩家行数相加，含访客；不能称为去重玩家人数 |
| 去重注册玩家数 | 基础集合中经 people.user_id 关联且非空的账号去重；另返回 named_player_count 去重全部 person_id；匿名只计人次 |
| 扩展使用局数 | 所选扩展在基础集合出现的不同 play_id 数；同局只用其两个模块仍计 1 次 |
| 独立扩展开局 | 独立扩展作为主游戏时算该作品的主游戏开局；与作为扩展使用分列展示 |
| 实际总时长 | SUM(已填写 duration_minutes)；同时返回已知时长局数及缺失局数；不把 NULL 当 0 |
| 平均局长 | 已知时长总和 / 有时长的完成局数；全未知则 null |
| 我的游玩时长 | 本人实际参加局的已知时长相加，不乘参与人数 |
| 未完成数 | published 且 stats_exclusion!='all'、status=abandoned，按同一筛选器独立统计；草稿、作废不进完成指标 |
| 最近开局 | MAX(played_on)，精确时间未知就显示日期；不编造开始时刻 |

所有总数及行明细必须共用过滤器。游戏/实物归档或活动删除不会使真实完成局消失；作废对局则从基础集合移除。该用户只是代记他人一局，不增加他自己的参局数或时长。

## 3. 胜负、得分和名次

### 3.1 竞技胜率

个人竞技和团队竞技分别显示，不默认合并；合作与单人另外展示成功率。个人竞技结果取玩家行，团队竞技取队伍行并映射到本队玩家，不能从队友人数重复累加同一人的结果。

`eligible_games` 是基础集合中对应竞技模式、stats_exclusion=none，且该玩家/队伍结果明确的不同对局数：包括整局 resolved，以及整局尚 unknown 但该成员 gave_up 的明确未获胜。`wins` 计 outcome=win，`draws` 计 draw，`losses` 计 loss；三者之和等于 eligible_games。

`win_rate = wins / eligible_games`。平局进入分母、不是半个胜场；并列胜出按每人一场胜利，所以所有玩家的胜率之和不必等于 100%。结果未知的主体、未完、作废、单人和合作都不进竞技分母；完成局 gave_up 的成员属于已知未获胜，不是未知结果。

胜率榜必须选择某一款游戏和竞技模式；可以进一步限制人数、变体和扩展。有 1 局有效样本即可上榜（D07），仍显示有效局数；0 局有结果时 win_rate/rank 为 null，不能把未知当 0% 或 100%。跨游戏只提供参局次数榜，不编造综合实力积分、Elo 或竞技等级。

### 3.2 合作与单人

合作成功率在基础集合中取 cooperative、result_status=resolved 且 stats_exclusion=none 的记录，计算 success 局数 / (success + failure 局数)。全体按局，个人按本人参加的局；个人 gave_up 为失败，其他成员结果不变。未知主体不进分母。单人 success/failure 用相同规则单独统计，避免把独自挑战成功次数混到多人合作或竞技胜场中。

### 3.3 分数与名次的可比性

分数比较只在同一 comparison_key 内：相同主游戏、规则/变体版本、计分方向、实际人数、扩展组合及稳定规则配置；团队还包含队伍人数结构。界面先展示可选组及样本数，未选定组不返回跨组最高分或平均分排行榜。

平均分从基础集合使用已填写分数的样本，0、负数均有效，NULL 排除；stats_exclusion=wins 只排除胜负/成功率统计，仍可计入完成局数和分数/名次统计。结果未知但分数已真实记录的完成局可以参与分数统计，因此 `score_samples` 与 `eligible_games` 可能不同，必须分别显示。最佳分 high 取 MAX、low 取 MIN；manual/none 未声明分数比较方向，不排序“最高水平”。团队只有队伍分数表，不复制成个人平均分；合作共同分也按局展示。

平均名次仅在同游戏、同模式、同实际人数/队伍结构及规则组中，对非空 rank 求平均。rank 是整局录入结果，不按当前页面筛到的玩家重新编号；筛出一名第三名仍显示第三名。手动名次不要求一定有分数。

### 3.4 排名和时间趋势

同主指标值采用竞赛排名 `1,1,3`（RANK），不使用 `1,2,3` 假装没有并列。相同胜率按样本数降序、person_id 升序稳定展示，但仍共享名次；胜率排序比较精确分数，显示百分比可四舍五入到一位小数，不能先舍入再定名次。

日期趋势的 bucket=day/month/quarter/year 按上海实际日期分桶；bucket=activity 按原活动 ID 分组，未关联活动单列，无局日期填 0，真实时长未知继续为 null/缺失样本而非 0。跨午夜对局按开始所在 played_on 归桶；无精确时间按明确填写的实际游玩日期 played_on 归桶，不能改用 created_at。默认近 12 个自然月（本月至前 11 月），其他榜单默认全部；响应回显实际日期范围，避免趋势和总览看似矛盾。

## 4. 一期展示的数据表

| 数据表 | 默认列 | 钻取 |
| --- | --- | --- |
| 全体最想开 | 排名、游戏、累计提名人次、活动场数 | 有效提名活动和人数 |
| 我的最想开 | 排名、游戏、我的提名活动数、全体提名人次 | 我在哪些活动提名 |
| 全体/我的开的最多 | 排名、游戏、已完成局数、最近开局 | 符合筛选的实际对局 |
| 玩家参局榜 | 排名、玩家、参局数、游戏款数、最近参局 | 此人在小程序内公开的参局记录 |
| 单款玩家成绩 | 玩家、参局数、结果样本、胜/平/负、胜率、上榜资格；选可比组后加均分/最佳分/平均名次 | 该玩家该组的对局 |
| 扩展使用表 | 扩展、所配本体、使用局数、最近使用 | 使用该扩展的对局 |
| 个人概览 | 完成局、游戏款数、已记录时长及缺失数、分模式结果样本；选游戏后给胜率/成功率 | 分模式展开 |
| 时间趋势 | 日期/月、完成局数、参局人次、已知时长 | 当期对局 |

“查看他人”展开其已发布公开记录；`scope=mine` 表示只筛本人实际参与，不是一种私密可见模式。页面上的日期、范围、人数门槛和“已记录”限定必须可见。数据为零时给出记录入口，不展示虚构排名或 0% 代替未知。

## 5. 可重复的统计设计验算

本目录的 [statistics-fixtures.sql](statistics-fixtures.sql) 与 [verify_design.py](verify_design.py) 用完全虚构的数据、内存 SQLite 检验上述统计公式和关键反例；它们是**设计验算工具，不是业务实现或 MySQL 迁移测试**。fixture 只含计算所需的简化字段，不可当成生产建表脚本。

运行：

```sh
python3 backend/design/boardgame-library/verify_design.py
```

人工预期包含：两人跨两活动提名同游戏→3 人次/2 活动；取消/撤回/失去资格不计；一局两扩展不增加完成局数；同款多局分别计；个人代记不等于参局；活动外公开局进入全体、held 导入局不进入；团队/合作/平局/未知结果的分母分开；0 分和负分保留；删除活动保留完成局。

## 8. 本地验证、部署与回滚

本轮交付技术方案、参考 DDL 与隔离验证工具，可审阅的变更范围为入口文档、本目录和后端 README；没有可部署的功能提交，不需要项目业务库迁移或现有服务重启。临时 MySQL 参考结构检查结果见验证记录。

实现阶段新增迁移应从实施时重新确认的 head 接续，先在本地 MySQL 克隆结构/虚构数据上 upgrade；SQLite 快测不能证明 MySQL 外键、JSON 和锁行为。运行后端 pytest、相关小程序 Node 测试与实际微信流程，报告通过数和设备缺口。对已有活动/报名/签到/旧排行榜做回归，旧统计不悄悄切换为新对局统计。

供线上运维项目的部署包应包含提交 SHA、新迁移列表、功能开关、导入 worker 启停与健康检查、独立 BGG 网络开关、媒体及非公开导入目录权限、上游配置变量名（不含值）、备份步骤和本地验收记录。部署顺序为备份→加表迁移→兼容后端/worker→小程序入口；一期开关未开启前旧页面正常使用。以上是执行说明，不授权本任务连接线上。

回滚优先关闭新入口和导入 worker，恢复兼容的应用版本，保留已产生的新业务数据。**新表已有引用后不能直接回退到原版活动删除代码**：数据库会 SET NULL，但旧代码不会补快照/审计；需使用含兼容删除保护的回滚版本，或在回滚期间禁用活动硬删除。不能直接 downgrade 删除存有实物、对局和成绩的新表；需导出/备份并由运维另行确认处理。来源导入问题按来源与审计修复，不删除手动补录数据。

## 9. v3.1 扩展公式及验算

天数/H-index/次数里程碑、人物/地点/环境/人数/扩展筛选、初玩、伙伴和角色的规范公式以 08 第 3–4 节为准；计分表模板可比性、投影有效性、分项样本和贡献占比以 08 第 5 节为准。新增 fixture/checks 用虚构数据独立验证这些反例，基础 42 项保留并通过 people 关联账号验证原口径；不是复制旧 user_id 玩家模型。

分模式全体样本分别为 individual 玩家结果、team 队伍结果、cooperative/solo 对局；指定主体时为该人的玩家/队伍/参局结果。指标回传 sample_unit，不将这四类样本简单相加称总局数。分数和结果分别校验，表格展示真实缺失原因。

所有统计先筛唯一 play_id 后分别聚合，player/expansion/cell 不直接交叉联表。普通公开统计不使用完整原件；cell 查询索引以 sheet_comparison_key 筛表后按 sheet_id/row_key 聚合，EXPLAIN 后调整索引。2 百万 cell 的性能是实施目标而非本轮实测结果。
