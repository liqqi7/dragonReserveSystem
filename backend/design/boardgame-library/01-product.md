> 此文保留3.1基线推导/验收项；3.2增加记分纸计算、个人收藏/成本、受控历史发布及真实小程序页面。当前字段、行为与已测范围以[实施契约](12-v3.2-implementation-contract.md)及[验证报告](verification.md)为准。

最新实施细则见 [3.1 实施契约](09-implementation-contract.md)。

属于 [桌游库 v3.1 设计](../../boardgame-library-scope.md)。已按用户确认的 D01–D08 更新；历史导入数据的展示策略暂留待后定。

## 1. 使用对象与基本关系

“游戏资料”是一款作品，“库存”是某个人或俱乐部拥有的一盒。“活动提名”表示想玩，“活动计划”表示准备安排，“实际对局”才表示确实玩过。三者可以不同，改计划不得改历史对局。

例如：liqqi 和小王各有一盒《卡坦岛》，俱乐部有《航海家》《城市与骑士》。活动计划可以选 liqqi 的本体和俱乐部的《航海家》；当天只玩本体也允许，实际对局中去掉扩展即可。另一桌玩同款、同一桌再来一局，各有独立对局 ID；绝不按游戏名称或日期自动合并。

一个扩展可兼容多个本体；独立可玩的扩展仍保留扩展类型，并标记 `is_standalone=true`。套装、合辑先按实物实际对应的资料登记，不能因为 BGG 名称相似就拆成多盒。只使用扩展的一部分模块时，选择该扩展并填写 `modules_note`；一期不建设所有游戏的模块规则库。

## 2. 小程序页面与入口

接入现有工具页桌游库入口；不改日程页原生 swiper 和 WXS。下列是新增业务页面建议名，不表示代码已经存在。

| 页面 | 展示与操作 |
| --- | --- |
| `boardgame_library` 桌游库 | 本地名称/别名搜索；全部资料、可供活动、我的库存筛选；本体/扩展切换；封面、名称、人数/时长参考、可用盒数；进入两个榜单 |
| `boardgame_detail` 桌游详情 | 本地显示资料、BGG 来源链接/同步时间、库存列表、兼容扩展、已记录对局、全体/我的统计；有权限时编辑或登记库存 |
| `boardgame_edit` 资料录入 | 名称→BGG候选→选择版本→确认；本地只查重，手填为后备；图片输入后续接入 |
| `boardgame_inventory_edit` 库存录入 | 游戏、持有者、状态、日期、版本/语言、存放位置、活动可用性、照片、备注、排序 |
| `boardgame_import` 导入任务 | 管理员输入 BGG 用户名或上传 BG Stats 文件，显示抓取/解析进度；逐项确认归属、游戏/玩家映射和重复处理，再应用；历史对局暂不公开 |
| 现有 `activity_detail` 新增桌游区 | 分别显示“想玩提名”“计划游戏”“实际对局”；可由提名加入计划，由计划新建对局 |
| `boardgame_play_edit` 对局表单 | 快速记录和成绩详情两级信息；选择实际玩家/访客、实际扩展；可保存草稿或完成一局 |
| `boardgame_play_detail` 对局详情 | 游戏、扩展、日期、地点、参与者/成绩、记录者、修改历史；再来一局、更正、报错、作废 |
| `boardgame_plays` 对局列表 | 全体/我的、游戏、活动、月份/季度/年度/自定义日期、来源筛选；已发布记录在小程序内公开；未完成单独入口 |
| `boardgame_stats` 数据与排行 | 游戏开局、玩家参局、单款成绩/胜率、扩展使用、时间趋势；所有数值可进入来源对局或提名列表 |

库内默认排序为 `sort_order ASC, name ASC, id ASC`。用户可切换最近添加、最想开、开的最多；扩展单独筛选，不能把“作为扩展被使用”混称为本体开局。首页可用盒数只统计明确可用且允许活动使用的库存，不把待核实、借出、停用、出库算进去。

图片失败用统一占位图；未知人数/时长显示“未填写”，无成绩显示“未记录”。无资料、无库存、无提名、无对局、筛选无结果分别有对应空态。BGG 不可用时保留手动录入入口；保存失败保留表单；重复点击提交不会重复造盒或造局。

表格在手机端优先展示名称、主指标和样本数；成绩等宽表可横向滚动，不强行缩小字号。详情中的人员/结果列表使用项目规定的信息展示抽屉；多输入表单使用表单抽屉或独立页；日期使用独立 Picker。具体视觉制作仍需按 `AGENTS.md` 验收，不在本轮凭空添加新的弹窗规范。

## 3. 录入资料和实物

2026-09-13 用户明确的现行录入要求为 [图片/名称 → BGG 搜索 → 返回候选资料 → 用户选择正确条目及版次 → 实物信息 → 保存](13-photo-recognition.md)。以下 3.1 的手工创建作为未找到正确结果或来源不可用时的后备能力；不再采用先手工建资料的默认入口。本地查重不跳过用户的 BGG 候选选择。名称部分已完成，见 [实现契约](14-name-intake.md)。

### 3.1 手动录入

1. 先搜索本地资料；存在则复用，点击“登记一盒”。
2. 不存在时，填写名称、类型；可补别名、封面、简介、人数和时长。保存资料即取得本地 ID，可立即提名，无需先有库存。
3. 登记库存时明确选择归属，不能默认把录入者、BGG 用户或放在店里的人当成所有者。普通成员仅可登记本人；管理员可选俱乐部、本地成员、外部持有者。
4. 一次录入多盒可填数量 1–20，服务端原子创建 N 条独立库存，各有 ID。修改时按盒操作，没有独立可编辑的“总库存数”。
5. 本地照片可使用相机或相册上传。拍封面供展示不调用识别或翻译服务。

归属展示公开到昵称/俱乐部/外部名称；准确存放地址、购入日期和内部备注仅库存所有者、管理员可见。活动组织者只获得安排所需的可用状态、语言版本、携带人和适当的地点提示，不通过库存接口泄露个人地址。

### 3.2 BGG 录入和导入

搜索候选显示 BGG ID、原文名称、年份、类型和缩略图，由人选中；同名不自动绑定。选中详情后可改中文展示名。BGG 默认英文名和完整来源数据保留。

导入 liqqi 的流程是：拉取收藏→预览拥有标志及版本→匹配本地 BGG ID→指定本地所有者→选择新增/关联已有实物/仅补资料/跳过→应用。首次导入库存默认“待核实”、不可供活动；持有者或管理员核对后改为可用。重复应用和重复导入幂等；收藏不再出现某项只提示来源变化，不自动出库。

同款资料重复时，管理员进入合并预览，查看受影响的库存、扩展、活动和对局；明确选择保留的资料 ID 后执行事务合并。两条都有不同 BGG ID 时不直接合并，须先解除错误绑定。名称相同、不同语言或版本只提示候选。

## 4. 活动提名与计划

### 4.1 提名

活动创建者无需自己报名也能提名；普通成员必须仍在报名表中。管理员身份本身不等于替别人投票的权限。每个用户对同一活动的同款游戏只有一份有效提名；“我也想玩”就是新增自己的提名，展示去重人数及人员列表。

可提名未登记实物的游戏。选择非独立扩展时，先选兼容本体，记录为本体提名附带“希望使用”的扩展；提名人数仍归本体。每人可选择不同扩展组合；计划由组织者决定，不自动把全部提名扩展取并集。

活动开始时冻结提名，开始前有资格者可持续新增、修改、撤回，不提供提前锁定。退报名或被移出后，非创建者的有效提名变为失效，再报名不会自动恢复。冻结后保留截止时意愿，人员事后变动不改历史；活动取消、流局、逻辑删除后不进入最想开统计。硬删除活动时提名/计划随活动删除，已完成对局保留。

管理员可因误录移除提名，必须留操作原因和审计；不能伪装成用户投票。活动开始时间被推迟到未来时，以新的开始时间为准重新开放：仍有资格的 frozen 提名恢复 active，已撤回/失效/移除的提名不自动复活。修改时间事务需先按旧截止点结算，再应用新时间并记录审计；只改活动时间不改变已经真实发生的对局。

### 4.2 活动计划

组织者可从提名加入，也可自由添加未被提名的游戏。一个条目是一桌/一段准备玩的游戏，可填写桌号、携带人、实物、具体扩展、备注、顺序；同款可以有多个条目。

无库存时标记“实物待落实”，可先保存；本体与每个扩展各自选择实物。选择库存时检查作品是否匹配、状态及活动可用性；库存稍后借出/出库时计划显示警示，不把已保存条目悄悄换成别人的盒子。

一期计划属于安排信息，不实现库存借还和硬预约锁。相邻活动选择同一盒时显示时间冲突提示，由组织者协调；冲突不会改变库存所有权或阻止记录已经发生的对局。活动中的游戏人数、时长仅供参考，不自动覆盖活动报名上限或起止时间。

## 5. 最终玩了什么：实际对局

### 5.1 快速记一局

1. 活动内点击某个计划的“记一局”，或从实际对局区选择新游戏；独立入口可补录活动外的对局。
2. 预填游戏和计划扩展，用户确认本次实际组合；玩家候选来自活动报名表，但必须勾选实际参与者，不默认全员参局，不将签到等同于参局。
3. 选择实际日期（默认今天，活动内可建议活动日期）、至少一位实际玩家。允许补录未报名成员及临时访客；本活动已打卡参与者均可记录或代记其他桌，不要求记录者必须参局。创建者/管理员保留代记管理能力；其他普通成员仅报名未打卡时不可创建活动对局。
4. 点击“完成一局”即产生一条已完成记录，计入开局次数；分数、胜负、时长可以未知。尚未确定实际参与者或尚未结束则存草稿，不计榜。
5. 多人玩同一局只需要一人登记，其他玩家在“我的对局”看到同一条记录。提交前提示同活动/游戏/玩家/相近时间的疑似重复，由人选择查看已有记录或明确继续；不自动吞掉同款第二局。

一次记录只代表一局，不提供把“玩了 3 次”写成同一条成绩的数量字段。“再来一局”复制游戏、扩展、地点、规则和玩家，清空分数、名次、胜负、时长和原日期时间，生成新的草稿与请求键。

### 5.2 成绩与特殊玩法

| 方式 | 录入内容 | 结果规则 |
| --- | --- | --- |
| 仅记参与 | 玩家；成绩可全空 | 计开局/参局；不进胜率、分数、名次样本 |
| 个人竞技 | 高分胜/低分胜/手动名次；每人可选分数 | 分数齐全才建议自动名次；同分提示确认并列胜出或平局；有破同分规则可手动改名次 |
| 团队竞技 | 至少两队、队名、各队队员；成绩记在队上 | 同队共享胜负及队伍名次，个人不复制队伍分数；至少两支非空队伍 |
| 合作/单人 | 团队成功、失败或未知；可选共享分数 | 不计算个人竞技胜率，单独显示合作成功率；单人不占竞技胜率榜 |
| 中途结束 | 状态“未完成”、可记录时长和说明 | 出现在历史的未完成筛选；不计完成开局、胜率和成绩榜 |

分数允许负数和小数，0 是有效分数，空值表示没有记录。手动判名次采用 1、1、3 的竞赛排名法；“并列第一且都算赢”和“平局无人获胜”明确区分。记录完成时结果可以未知；一旦选择计胜负模式，整局结果须完整且自洽，不能只填自己的赢、遗漏其他人的状态。

游戏资料可记默认规则和常用变体，实际对局保存规则快照。用户不会被要求理解内部比较键；页面只需选择“标准规则/已有变体/新变体”、高低分胜、人数和扩展，统计自动按可比条件分组。

### 5.3 可见范围、纠错和协作

已发布对局统一在小程序范围内公开，活动外独立对局也可查看，不提供仅本人可见模式；需要现有小程序登录，不因此新增互联网匿名接口。全体榜默认汇总全部已发布的完成局，活动筛选可缩小到某一场。“我的”仍按实际参局计算，不能把记录者代记的其他桌算到自己名下。独立手动记录由成员创建且应包含自己；管理员可代记线下局。

记录者、关联活动创建者、管理员可编辑对局。已打卡参与者获得记录权限，不自动获得修改其他人记录的权限；其他参局者可提交“记录有误”说明，生成持久报错记录并显示在记录者的待处理列表，不自动发微信、邮件等消息。更正填写原因，原版本保留。草稿仅记录者/组织者/管理员可看；导入但 held 的记录仅通过导入管理预览，不出现在普通公开入口。

打卡依据为当前报名记录的 checked_in_at 非空，现场打卡和管理员补打卡均有效。首次保存/完成活动对局时服务端再次校验；撤销打卡后不能新记活动局，已完成对局不被删除，原记录者仍可留痕纠错。实际参局人可以与打卡名单不同，不能为导入历史而伪造活动或签到。

作废使用状态变更和原因，立即从统计中移除，不物理删除；误作废可通过更正恢复为草稿/已完成/未完成，重新校验所有必填项。并发修改用版本号检测，旧页面保存返回冲突并展示新版本，不能后提交覆盖先提交。

活动结束不会自动生成任何对局，也不把计划批量转成已玩。历史活动可以后补真实对局。活动硬删除时记录活动名称、日期、原活动 ID、组织者的快照，脱离活动后的对局仍可查且可按原活动筛选；组织者纠错权限按快照保留并审计。库存/游戏归档也不删除历史成绩。

### 5.4 历史导入

一期接收 BGG 历史和 BG Stats 导出文件：先存原件，预览并确认游戏/玩家映射及重复项，再生成本地来源关系与对局。已具备完整日期/实际玩家的记录可规范为 completed 或 abandoned；缺失信息保存 held 草稿及问题清单，不编造分数、玩家或日期。导入成功不等于公开，统一先 held；展示和统计开放后续决定。操作和数据格式详见 [05 历史导入](05-history-import.md)。

## 6. 权限矩阵

下表“成员”指现有 `user` 或 `admin` 角色；登录后的 `guest` 可浏览非敏感资料及已发布公开对局，不可发起写入或查询成员目录。成员权限不可由客户端传入 `user_id` 冒充。

| 操作 | 普通成员 | 活动创建者 | 管理员 |
| --- | --- | --- | --- |
| 创建缺失资料 | 可以 | 可以 | 可以 |
| 编辑公共资料/BGG 绑定/关系全局维护 | 仅本人创建且未共享资料可编辑；可按确定 BGG 候选新建，既有资料绑定/解绑及合并不可 | 同普通成员 | 可以；导入原件和 held 内容不通过公开预览泄露 |
| 维护实物 | 本人库存，不能转给别人 | 同普通成员 | 所有库存；变更归属留痕 |
| 导入 BGG 收藏为实物 | 不可 | 不可 | 可以；明确目标归属 |
| 提名/撤回 | 已报名且未冻结，本人的提名 | 未冻结，本人的提名 | 遵守本人资格；另可移除违规记录 |
| 维护计划 | 不可 | 可以 | 可以 |
| 新增活动对局 | 已打卡的报名参与者，可代记本活动其他桌 | 可代记 | 可代记 |
| 改对局/作废 | 本人创建的记录 | 本活动记录 | 可以 |
| 读取已发布对局 | 小程序内可读，包括独立局 | 同普通成员 | 同普通成员 |
| 导入历史/查看 held | 一期由成员导入本人数据，管理员可代导 | 有管理员角色时可以 | 可以 |
| 单局报错 | 实际参局者或记录者 | 本活动 | 可以 |

“未共享资料”定义为：没有其他成员的库存、提名、计划、对局引用。编辑时事务内重新检查，不能只凭创建时标志。隐私范围和角色检查均在服务端执行；角色变成 guest 后停止写入，既有对局及历史投票不因此被删除。

## 7. BG Stats 的参考边界

参考它将本体与所用扩展放在同一次对局、按扩展查看使用记录的方式；本项目以本地游戏和 person 为对局身份，账号权限使用 users，不依赖用户安装 BG Stats。[BG Stats：Expansion Logging](https://www.bgstatsapp.com/explanations/expansion-logging/)

v3.1 正式纳入具名未注册玩家、地点/线上属性、计分表及扩展统计，见 [08](08-bgstats-statistics-coverage.md)；本项目采用统计文档里的明确口径，未承诺复刻其全部功能或打通其账号。[BG Stats：Power Expansion](https://www.bgstatsapp.com/expansions/power-expansion/)

## 8. v3.1 展示与统计流程

对局选人区分已注册成员、具名朋友、匿名槽位；具名朋友建立 person 后复用，匿名仅本局。管理员在预览后明确绑定账号或无冲突合并，不能按名字自动处理。成员可创建手录人物/地点，管理员维护和归档；导入的内部身份、地点不进入公共选项。

对局表单新增地点、线上/线下/未知及每人的初玩标记。详情可打开分组或轮次计分表，保留玩家/队伍列、0 分和缺失值；编辑名单时同步处理计分关联。已知数值可手填，未知公式不执行。

统计页加入天数、H-index、次数里程碑、星期/人数/环境分布、伙伴及地点表；游戏详情加入角色、分模式成绩、可比计分表分项。图表和表格均能按同一过滤条件钻取；无样本、无已知时长、未知结果、模板不可比各显示实际状态。计分表宽内容横向滚动，按 A35 真机检查长姓名、多轮次、键盘和安全区；当前尚未实现 UI。
