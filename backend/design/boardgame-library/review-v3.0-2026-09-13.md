# 技术方案 3.0 需求与流程审查

审查日期：2026-09-13；分支：codex/bgg-sync。审查对象为 [技术方案 3.0](../../boardgame-library-technical-solution.md)、全部配套契约、参考 DDL 和相关现有代码。集石、新物集及中文搜索接入按用户要求跳过。

本文件记录审查发现和修订建议，不修改已确认的业务规则，不表示问题已经修复。当前业务 API、模型迁移、持久导入和小程序页面仍未开发；工具页入口仍为占位。这里的“已覆盖”指已有设计，不能理解为已有可用功能。

## 2. 需要修订的设计

### RV01 — P1：已导入历史缺少明确的更正及差异应用流程

证据：[导入 DTO](06-api-contracts.md) 第 221、251、282 行；[来源变更规则](05-history-import.md) 第 77 行；[公开访问边界](03-api-and-bgg.md) 第 136 行。

导入决策只定义 create_play/link_play/skip，其中 link_play 明确只增加来源关系。普通对局接口不提供 held 记录的常规管理入口。另一方面，方案承诺保留不完整的 held 草稿，并在来源同 UUID 内容变化时展示差异；目前没有定义如何把这些差异或补全信息应用到既有局。

触发场景：第一版文件缺少日期或录错赢家，生成 held 草稿/待核对记录；第二版文件补全，或管理员在本地核对后需要更正。创建会遇到来源唯一键，关联不会改成绩，普通公开接口又不是此类记录的管理入口。实施者需要自行发明更新语义。

建议：增加任务权限范围内的既有导入局编辑和 update_existing 决策，明确目标版本、来源基线、本地人工更正优先级、冲突解决、可修改字段、审计及再次应用行为。更正后仍 held，不开放历史发布；支持草稿补全、误关联纠正和 source_changed 的明确处理结果。

验收：缺日期首次导入→补全后重导入→仍为同一 play_id；本地与来源同时改成绩必须明确决策；重试不重复，公开统计仍不变。

### RV02 — P1：重导入依赖的数据集标识没有完整的返回和查找契约

证据：[导入 DTO](06-api-contracts.md) 第 193–195 行；[导入接口目录](03-api-and-bgg.md) 第 224–231 行。

服务首次生成 source_dataset_id，重导入要求客户端传回该 ID，玩家/地点映射依赖此命名空间。但 ImportJob 返回字段及 params 白名单未列该 ID；接口目录也没有任务列表或数据集列表，只有已知任务 ID 的读取。

影响：用户回来续做、换设备或重导出文件时，缺少正式方式找回原任务和身份映射。若每次创建新数据集，新出现的对局可能为同一位朋友再建 person，历史统计被拆开；对局 UUID 去重不能解决人物映射复用。

建议：返回 source_dataset_id，增加仅本人可见的任务列表及数据集选择能力，明确继续同一数据集与新建数据集的入口、显示名称和权限。可先复用 jobs.params 实现，无需因此立即增加业务表。

验收：首次导入返回 ID；清除客户端缓存后可找回；同数据集第二个文件中的新局复用原 person/location；其他管理员不能枚举私人任务。

### RV03 — P2：部分统计可以显示，无法按现有参数准确回查

证据：[图表与回查 DTO](06-api-contracts.md) 第 310 行；[统计接口](03-api-and-bgg.md) 第 296、303–305 行；[共用筛选](08-bgstats-statistics-coverage.md) 第 51–65 行；[活动趋势](04-statistics-and-acceptance.md) 第 81 行。

星期分布返回 weekday 分组及 drilldown，但对局列表与共用过滤未定义星期筛选。活动趋势将未关联活动的局单列，却没有 activity_missing 等筛选条件。现有 location_missing 是地点条件，不能代替活动条件。

影响：点击跨多周的“星期六”或“未关联活动”分组，客户端无法用契约内参数精确取回对应局；只沿用日期区间会混入别的星期或活动。

建议：补 weekdays 和 activity_missing 等明确参数，规定互斥、AND/OR 及日期口径。对每个图表行执行“统计 ID 集合等于分页取回的 ID 集合”的集成验收，而非仅验一条计数 SQL。

### RV04 — P1：主方案残留删除重建明细的旧算法

证据：[主方案](../../boardgame-library-technical-solution.md) 第 129 行仍描述解除玩家队伍引用、删除旧队伍并重建；[v3 DTO](06-api-contracts.md) 第 18、111–113、342 行要求保留既有行 ID；[参考 DDL](database-schema.sql) 第 595–597 行对计分单元格建立同局引用。

影响：已有计分表的队伍/玩家若按旧算法删除，会被外键拒绝；主动删除引用绕过约束又会破坏计分关联。主方案与详细契约会指导出不同实现。

建议：删去旧算法，统一为保留未变行 ID 的差异更新；真正移除被引用主体时，同事务先调整或明确清除计分表，再处理成员/队伍。仅改队名或队分不应重建队伍 ID。

验收：带计分表改队名、改队分、换队及移除玩家；既有主体 ID 稳定，需删主体时显式处理引用，任一步失败整体回滚。

### RV05 — P2：自由备注会把相同玩法拆成不同统计组

证据：[数据字典](02-data-model.md) 第 191 行；[产品流程](01-product.md) 第 100 行；[规则 DTO](06-api-contracts.md) 第 34 行。

comparison_key 包含扩展 modules_note。即便格式规范化，用户填写“只用新地图”和“新地图”仍是不同文本，相同实际玩法就会被分组隔开。产品还承诺选择已有/新变体，但尚未明确稳定变体标识的创建、复用及查询契约。

建议：用稳定规则版本或可复用的玩法组合 ID 表示比较条件，模块备注用于说明；无法确认的组合继续标为不可比，不能通过忽略差异强行混组。一期不必建设所有桌游的模块规则库，但必须定义同一已确认组合的复用方式。

验收：同一已确认组合仅改显示备注不会改变可比组；真正换规则或模块会进入另一组；未知组合不混入已确认规则。

### RV06 — P2：库存误选作品后缺少安全纠正入口

证据：[库存 DTO](06-api-contracts.md) 第 48 行。

库存 PATCH 禁止 game_id，并将纠正指向导入/资料合并流程。但“这盒实物登记错游戏”不等于“两款游戏资料重复”。例如误将独立版登记成本体，不能为纠正一盒库存而合并两个真实作品；手录实物也未必有导入项可操作。

建议：补管理员库存纠正操作：预览受影响的计划和实际局，按版本确认目标作品、处理来源绑定并审计。没有引用时直接纠正；有历史引用时分别确认哪些确属误录，不能静默批量重写真实历史。

验收：手录错作品可纠正；其他库存不受影响；历史局保持原义；来源唯一键和计划引用仍有效。

## 3. 现有代码的关联问题

### RV07 — P2：签到时间窗口前后端不一致

证据：[活动后端](../../app/services/activity_service.py) 第 31、429–439 行：提前 30 分钟；[活动详情前端](../../../miniprogram/pages/activity_detail/activity_detail.js) 第 355 行：提前 60 分钟。

14:00 活动，前端 13:00 开放签到，后端 13:30 才接受。新功能以签到作为普通成员记局资格，因此应在联调前统一；建议由后端返回开放时间和当前权限，前端据此显示，不继续维护两份常量。具体提前多久属于既有签到规则，本次不擅自改动。

## 4. 使用上的取舍，不应混称已确认需求遗漏

- **计分表统计需要管理员审核模板。** 当前审核落在每局，只有已审核模板才参与分项统计，且未定义可复用的审核注册表。实际可能出现“录了许多计分表，分项统计仍无数据”。建议同游戏、同规范模板签名和规则版本复用审核；仅改分值不重审，行定义变化再审核。见 [计分表规则](08-bgstats-statistics-coverage.md) 第 101、109 行及 [审核接口](06-api-contracts.md) 第 338 行。这是减轻操作成本的建议，不是建议取消可比性校验。
- **BG Stats 文件当前只按对局导入。** 真实文件还含 201 条 statusOwned=1 的 copies，但方案只保留这些来源，不提供转成库存的确认流程。若用户期待一次导入同时迁移藏品，需单列收藏导入能力；201 条来源不能直接等同于 201 盒本地实物。见 [真实文件核验](07-bgstats-real-export.md) 第 24、83 行。
- **普通成员不能自己导入收藏或历史。** 现方案一期仅管理员操作。这会增加后续成员迁入数据的工作量；属于方案中的权限取舍，不应将 D08 的“一期可导入”解释为用户已明确拒绝成员自助。见 [权限矩阵](01-product.md) 第 127、133 行。
- **历史暂不公开仍是 D08。** 不因为现在有统计接口就发布导入历史，也不把 AI、OCR、翻译或已跳过的中文搜索接入重新列为本轮必修项。

## 5. 实际验证及边界

- 重新执行 verify_design.py：42 基础统计、16 生命周期/约束、26 v3 统计、5 身份/投影、13 基础导入、21 现代导入，共 123 个离线案例通过；另有 XML 合成响应往返、JSON 示例及 Markdown 链接检查。未提供官方额外样例，因此本轮不是旧报告所述的 124 项。
- 使用现有虚构 SQLite fixture 额外验证：删除已有计分表引用的玩家行触发 FOREIGN KEY constraint failed；回滚后 2 条玩家行和 5 条对应分项仍在。这个反例支持 RV04，不是 MySQL 服务层集成测试。
- 检查现有代码注册范围：没有新增桌游业务路由/模型/迁移，小程序工具入口仍调用占位提示。
- RV01–RV03、RV05–RV06 为契约走查和具体场景推演，未实现 HTTP 接口，因此没有声称获得真实 HTTP 错误响应。
- 未修改方案 3.0、业务代码或数据库；未连接生产；本轮不重复运行旧 MySQL 参考建表验证，不将其当作当前 API 或性能验收。

建议先修 RV01、RV02、RV04，再补 RV03、RV05、RV06，并将 RV07 纳入活动联调。修订应同步路径、DTO、事务、DDL（如需要）和验收案例；保留 D01–D08 的既有决定。开发仍可按可交付闭环分批：资料/库存→提名/计划→记局和基础榜单→历史导入与完整扩展统计，各批均包含相应界面验收。
