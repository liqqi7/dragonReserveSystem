## 4. 已确认的问题及实现风险

### 已复现/已证实

1. V2 创建和更新携带 sub_items 均得到 Schema extra_forbidden，实际 HTTP 合约将拒绝此字段。
2. ActivityDetailV2Response 没有 sub_items；ActivitySignupRequest 虽已定义，但 V2 路由未使用。
3. 备注上限仍是前后端 120；200 字输入被 Schema 拒绝，与原型计数不一致。
4. ActivitySubItemInput 接受纯空格名称，需要 trim 后必填校验。
5. 没有最多 4 项、同活动归属、重复 ID、项目容量与总容量联动的完整校验。
6. 现有报名服务是先 count 再 insert，无容量锁定；新增多项目不能延续这种并发超卖风险。需事务内按稳定顺序锁定/等效原子容量校验，并保证一次报名全成或全败。
7. 新关联表中的 activity_id/user_id/participant_id/sub_item_id 各自有外键，但没有保证彼此属于同一活动/用户；服务必须校验，不接收客户端自填关联身份。
8. 现有自动测试没有子项目专项覆盖；全绿只证明选定旧功能回归通过。

### 需在实现时防止的关联问题

- 一人选多个项目仍只占一个活动总名额，项目人数不能相加当活动人数。
- 同时抢最后名额、重复点击、超时重试、选中后已满、非法项目 ID 应给明确反馈且不残留半条报名。
- 编辑项目必须保留稳定 ID；省略字段不等于清空，空数组的意义需明确。
- 已有人报名的项目删除/关闭开关/降低容量需要保护，禁止静默丢掉报名。
- 退出活动、管理员移除、活动删除须同步清理关联；签到和统计暂保留活动维度。
- 我的活动、首页、详情及参与人缓存更新一致；不为列表引入无控制的 N+1 查询。
- signed_up 是按当前登录人计算，详情接口目前丢弃了可选用户参数的用途，接入时须明确匿名与登录用户输出。
- 原型详情背景示例为 2 项，报名抽屉示例为 4 项且同名容量状态不同；实现必须共用同一份实时数据，不能硬编码示例。
